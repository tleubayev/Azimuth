# Handover Runbook — Compass on Telegram (azimuth)

This runbook hands the **Telegram Mini App** (`telegram-mini-app/`) over to an independent KOL so
they can run it from **their own repository** and under **their own accounts** (Telegram bot, Privy,
Vercel) while still trading against the Compass API.

Follow the sections **in order** — several values produced in one step are required inputs to a
later step. Budget ~60–90 minutes for a first run.

> What the app is: a from-scratch Next.js 15 trading UI for Compass tokenized assets + Hyperliquid
> perps, funded from a TON wallet. Telegram only exposes TON wallets, so it uses **Privy** (seamless
> Telegram login → embedded EVM wallet that signs all trades), **TON Connect** (the user's TON wallet
> for funding), and **Symbiosis** (TON→EVM bridge). See `README.md` / `CLAUDE.md` for architecture.

---

## 0. Ownership model — what the KOL owns vs. what Compass keeps

| Resource | Owned by | Notes |
|----------|----------|-------|
| Source repository | **KOL** | A standalone repo created from a zip of `telegram-mini-app/` (see §1). |
| Telegram bot + Mini App | **KOL** | New bot via BotFather under the KOL's Telegram account. |
| Privy app + authorization key | **KOL** | New Privy app. Holds the embedded wallets + server-signing key. **Most sensitive** — see §3. |
| Vercel project | **KOL** | New project pointing at the KOL's standalone repo. |
| Compass API key | **Compass** issues → KOL uses | Server-only, never shipped to the browser. Compass can rotate/revoke. |
| RPC URLs | KOL or Compass | Any reliable Ethereum/Arbitrum/Base/HyperEVM endpoints (Alchemy/Infura/etc.). |
| Symbiosis partner id | optional | For bridge fee attribution; app works without it. |
| Fee recipient wallets | **KOL** (optional) | Revenue levers: a Hyperliquid builder address (perps) + an EVM address (spot sells). Both **off unless set** — see §4. |

The KOL operates the app from an **independent repository** (not the Compass monorepo) — they control
deploys, env, and their own merge history. §1 covers turning the provided code zip into that repo.

## 1. Stand up the standalone repo (zip → own repo)

The Mini App is **self-contained** inside the monorepo's `telegram-mini-app/` folder — it has no
workspace links (it depends on the **published** `@compass-labs/widgets` from npm, pinned in
`package.json`), no parent-relative imports, and ships its own `tsconfig.json`, `next.config.ts`,
`.npmrc`, and `.gitignore`. So the folder can be lifted out as-is into the KOL's repository.

1. Get the code as a **zip of just the `telegram-mini-app/` folder** (Compass provides this). Unzip it.
2. The unzipped folder's **contents** become the **root** of the new repo — i.e. `package.json`,
   `app/`, `lib/`, `components/`, `next.config.ts`, `.npmrc`, `.env.example`, etc. sit at the **repo
   root**. Do **not** nest them under a `telegram-mini-app/` subfolder (that keeps the Vercel **Root
   Directory** at the repo root — see §5a).
3. Create the repo and push:
   ```bash
   cd <unzipped-folder>          # confirm package.json / app / lib are HERE, not one level down
   git init
   git add .
   git commit -m "Initial import: Compass on Telegram (azimuth)"
   git branch -M main
   git remote add origin git@github.com:<kol-account>/<repo>.git
   git push -u origin main
   ```
4. Sanity-check it builds standalone **before** wiring up services:
   ```bash
   npm install                  # .npmrc pins legacy-peer-deps=true, so peer-dep conflicts resolve
   cp .env.example .env.local    # fill in later; a build does not need real secrets
   npm run typecheck && npm run lint && npm run build
   ```

> **Zip hygiene:** the zip should **exclude** `node_modules/` and `.next/` (regenerated by
> `npm install` / `npm run build`) and any real `.env`/`.env*.local` files. It **must include**
> `.env.example` (the canonical env var list), `.npmrc`, and the dotfiles. `.env`, `.env.local`, and
> `.env*.local` are already gitignored, so secrets won't be committed.

> **Staying in sync:** once extracted, the KOL's repo diverges from the Compass monorepo. Pull future
> fixes by copying changed files from `telegram-mini-app/` over, or by Compass shipping an updated zip.

## 2. Telegram — BotFather

Done in the Telegram app, chatting with [@BotFather](https://t.me/BotFather).

1. `/newbot` → choose a name + username → **save the bot token**.
   → this is `TELEGRAM_BOT_TOKEN` (server-only; also the HMAC key that verifies Telegram `initData`).
2. `/newapp` (or later `/setmenubutton`) for that bot → attach the **HTTPS Web App URL** = the Vercel
   production URL from §5. (You can create the bot now and come back to set the URL once Vercel is up.)
3. `/setdomain` → register the app's domain.
   - **Do NOT use a `.xyz` domain** — Telegram auth rejects it. The default `*.vercel.app` URL is fine.
4. (optional polish) `/setdescription`, `/setabouttext`, `/setuserpic`, and a `/setcommands` list.

> The bot token is the single most important Telegram secret. If it leaks, regenerate it in BotFather
> (`/revoke` → new token) and update `TELEGRAM_BOT_TOKEN` (and `NONCE_SECRET` if it was falling back to it).

## 3. Privy — embedded wallet + server-side signing

Create the app at <https://dashboard.privy.io>. This is where users' embedded EVM wallets live and
where the server-signing key is configured so **the user is never prompted to sign**.

### 3a. App + login method
1. **Create a new app** → copy the **App ID** → `NEXT_PUBLIC_PRIVY_APP_ID`.
2. Create an **App secret** → `PRIVY_APP_SECRET` (server-only).
3. **Login methods**: enable **Telegram ONLY**. Paste the bot token + bot handle from §2 and enable
   seamless / Mini-App login.
   - **Do not** enable email, social OAuth, or passkeys — popup/passkey flows are **blocked inside the
     Telegram WebView** and seamless Telegram login is the sole sign-in path.

### 3b. Embedded wallets
4. Enable **embedded wallets** for **Ethereum**, creation policy = **all users** (the code sets
   `createOnLogin: 'all-users'` and `showWalletUIs: false`, so confirmation modals never surface).

### 3c. Server-side signing key (required — no sign prompts)
5. Create an **authorization key / key quorum**:
   - Put its **id** in `NEXT_PUBLIC_PRIVY_AUTHORIZATION_KEY_ID` (client — used by `useDelegateWallet`
     to delegate each new wallet to the server).
   - Put its **private key** in `PRIVY_AUTHORIZATION_KEY` (server — used by `lib/server/privy.ts`).
     Base64 PKCS8; a `wallet-auth:` prefix, if present, is stripped automatically.
6. **Eliminate the one-time on-device delegation prompt.** Do **at least one** of:
   - (a) Enable **automatic delegation of embedded wallets at creation** to that key quorum, **or**
   - (b) Put the app on the **user-controlled server wallets (TEE)** execution stack.
   - On the legacy on-device stack, granting a signer can require an owner confirmation that
     `showWalletUIs: false` hides but cannot fully guarantee. This setting lives **only in the
     dashboard** — it cannot be set from the repo.

### 3d. Allowed domains
7. Add to Privy's **allowed domains**: `https://web.telegram.org` **and** the Vercel production origin
   from §5 (e.g. `https://<project>.vercel.app`). Update this whenever the deploy URL changes.

> **Migration note:** embedded wallets are scoped to the Privy app. Moving to a *new* Privy app means
> users get *new* embedded wallets (the old funded ones don't carry over). For a clean KOL launch with
> no existing users this is fine. If existing users must be preserved, transfer ownership of the
> *existing* Privy app to the KOL instead of creating a new one, and keep the same `NEXT_PUBLIC_PRIVY_APP_ID`.

### 3e. (Optional) TON-keyed identity
Only if you want the embedded wallet keyed to the TON address instead of the Telegram account:
enable **JWT-based auth** in Privy, set the JWKS URL to `https://<app>/.well-known/jwks.json`, set
`NEXT_PUBLIC_ENABLE_TON_KEYED_IDENTITY=true` + the `PRIVY_JWT_*` vars, and add a `/api/ton/privy-token`
route that mints the JWT (`lib/auth/mintPrivyJwt.ts`). **Leave disabled (`false`) for a normal launch.**

## 4. Compass API, Symbiosis, RPCs

### Compass
- Compass issues a **`COMPASS_API_KEY`** for the KOL. It is server-only — the `/api/compass/*` proxy
  (`app/api/compass/[...path]/route.ts`) attaches it as `x-api-key`; it is **never** exposed to the browser.
- `COMPASS_API_SERVER_URL` is optional (defaults to `https://api.compasslabs.ai`).

### RPC URLs (server-only, for gas-sponsored writes)
Provide reliable endpoints (Alchemy, Infura, QuickNode, etc.):
- `ETHEREUM_MAINNET_RPC_URL`, `ARBITRUM_MAINNET_RPC_URL`, `BASE_MAINNET_RPC_URL`, `HYPEREVM_MAINNET_RPC_URL`
- `GAS_SPONSOR_PK` — optional private key that sponsors gas for embedded-wallet writes (so users hold
  no native gas). Fund this wallet with a little ETH on each chain it sponsors.

### Symbiosis (TON→EVM bridge) — optional
- Request a `partnerId` / client id for fee attribution → `SYMBIOSIS_PARTNER_ID` and
  `NEXT_PUBLIC_SYMBIOSIS_CLIENT_ID`. The bridge works without these; they're only for revenue share.

### Hyperliquid perps — builder fee (optional revenue + funding)
Perps orders can carry a **Hyperliquid builder fee**: **0.1% charged on perps closes** (opens are
free), paid to a builder address the KOL controls. Set `NEXT_PUBLIC_PERPS_BUILDER_ADDRESS` to that
address to turn it on — the custom `global-markets-perps/{market-order,approve-builder-fee}` routes
inject it **server-side** (`lib/config/perps.ts`), so a client can't strip or change it. The address
is public (it appears on-chain in every order). **Leave it UNSET to run perps fee-free** — then the
funding step below does not apply.

**If the fee is enabled, you MUST keep the builder account funded.** Hyperliquid only lets a builder
collect fees once that **builder address holds ≥ 100 USDC in its Hyperliquid perp account**. If it is
unfunded, both the one-time builder approval and every fee-bearing close are **rejected**, and perps
trading breaks for users.

- Before launch, **deposit USDC into the builder's Hyperliquid account** (bridge USDC to the HL Bridge2
  on Arbitrum — `0x2Df1c51E09aECF9cacB7bc98cB1742757f163dF7` — from the builder address, the same path
  the app uses to fund users).
- Top it up periodically — it must stay above the minimum for fee-bearing trades to keep working. This
  is separate from `GAS_SPONSOR_PK` (EVM gas only) and from each user's own perps balance.

### Spot (tokenized assets) — partner fee (optional revenue)
A partner fee on **spot sells only** (exit-only, so it is always taken in USDC out of the proceeds —
buys are never charged). Set `NEXT_PUBLIC_TOKENIZED_FEE_ADDRESS` to your recipient address and,
optionally, `NEXT_PUBLIC_TOKENIZED_FEE_PERCENT` (percent of the USDC proceeds, default `1` = 1%). The
custom `tokenized-assets/sell` and `tokenized-assets/order/{hash}/charge_fee` routes inject it
**server-side** (`lib/config/tokenized.ts`): for **Midas RWA** it rides inside the sell transaction
(atomic); for **Ondo equities** it is a **seamless post-fill charge** (the embedded wallet auto-signs,
no prompt). **Leave `…FEE_ADDRESS` UNSET to run spot fee-free.** The recipient is public (on-chain).
Unlike the perps builder fee, this needs **no extra funding** — it is simply skimmed from each sell.

## 5. Vercel — project + deploy

The app ships **no `vercel.json`**, so the **Root Directory** and env vars are configured in the
Vercel project UI.

### 5a. Create the project
1. <https://vercel.com> → **Add New → Project** → import the KOL's **standalone repo** from §1.
2. **Root Directory** → leave as the **repo root** (`./`), since §1 placed the app at the root.
   - (If you instead kept the app inside a `telegram-mini-app/` subfolder, set Root Directory to that.)
3. Framework preset: **Next.js** (auto-detected). Build command `next build`, output auto.
4. Node 20+.

> Install note: the project pins `legacy-peer-deps=true` via `.npmrc`, so Vercel's `npm install`
> resolves peer-dep conflicts automatically — no extra install flag needed.

### 5b. Environment variables
Add **all** of the following in **Project → Settings → Environment Variables** (Production, and
Preview if you use preview deploys). `NEXT_PUBLIC_*` vars are baked into the client bundle at build
time — **redeploy after changing any of them.**

**Required**

| Variable | Source | Scope |
|----------|--------|-------|
| `COMPASS_API_KEY` | Compass (§4) | server |
| `NEXT_PUBLIC_PRIVY_APP_ID` | Privy app id (§3a) | client |
| `PRIVY_APP_SECRET` | Privy app secret (§3a) | server |
| `PRIVY_AUTHORIZATION_KEY` | Privy key quorum private key (§3c) | server |
| `NEXT_PUBLIC_PRIVY_AUTHORIZATION_KEY_ID` | Privy key quorum id (§3c) | client |
| `TELEGRAM_BOT_TOKEN` | BotFather (§2) | server |
| `NEXT_PUBLIC_APP_URL` | the production origin, e.g. `https://<project>.vercel.app` (§5c) | client |
| `NONCE_SECRET` | a long random string you generate (e.g. `openssl rand -hex 32`) | server |
| `ETHEREUM_MAINNET_RPC_URL` | RPC provider (§4) | server |
| `ARBITRUM_MAINNET_RPC_URL` | RPC provider (§4) | server |
| `BASE_MAINNET_RPC_URL` | RPC provider (§4) | server |
| `HYPEREVM_MAINNET_RPC_URL` | RPC provider (§4) | server |

> `NONCE_SECRET` signs `ton_proof` nonces and the session cookie. In production **one of**
> `NONCE_SECRET` or `TELEGRAM_BOT_TOKEN` MUST be set (`lib/server/secret.ts` hard-fails otherwise) so
> tokens verify across serverless instances. Set `NONCE_SECRET` explicitly — don't rely on the fallback.

**Optional**

| Variable | Default / purpose |
|----------|-------------------|
| `COMPASS_API_SERVER_URL` | `https://api.compasslabs.ai` |
| `PRIVY_APP_ID` | falls back to `NEXT_PUBLIC_PRIVY_APP_ID` server-side |
| `GAS_SPONSOR_PK` | gas sponsor key for sponsored writes (§4) |
| `NEXT_PUBLIC_PERPS_BUILDER_ADDRESS` | perps builder-fee recipient — also needs HL funding (§4); unset = no perps fee |
| `NEXT_PUBLIC_TOKENIZED_FEE_ADDRESS` | spot sell-fee recipient (§4); unset = no spot fee |
| `NEXT_PUBLIC_TOKENIZED_FEE_PERCENT` | spot fee as % of USDC proceeds, default `1` (§4) |
| `SYMBIOSIS_PARTNER_ID`, `NEXT_PUBLIC_SYMBIOSIS_CLIENT_ID` | bridge fee attribution (§4) |
| `SYMBIOSIS_API_URL` | `https://api.symbiosis.finance/crosschain` |
| `SYMBIOSIS_TON_TOKEN_IN` | `TON` (jetton master addr or `TON`) |
| `NEXT_PUBLIC_TONCONNECT_MANIFEST_URL` | leave **unset** — manifest is served dynamically (§6) |
| `NEXT_PUBLIC_ENABLE_TON_KEYED_IDENTITY` + `PRIVY_JWT_*` | TON-keyed identity (§3e), leave off |

### 5c. The chicken-and-egg URL
`NEXT_PUBLIC_APP_URL`, BotFather's Web App URL, and Privy's allowed domains all need the final
production origin. Order of operations:
1. Deploy once to get the assigned `https://<project>.vercel.app` URL (or attach a custom domain — **not `.xyz`**).
2. Set `NEXT_PUBLIC_APP_URL` to that exact origin and **redeploy** (it's a `NEXT_PUBLIC_` var).
3. Back-fill that URL into **BotFather** (§2.2 / §2.3) and **Privy allowed domains** (§3d).

> If you later add a custom domain, update `NEXT_PUBLIC_APP_URL`, BotFather domain, and Privy domains
> together, then redeploy — `NEXT_PUBLIC_APP_URL` is also the allowed `ton_proof` domain, so a mismatch
> breaks TON wallet sign-in.

## 6. TON Connect manifest (no action, just verify)

The manifest is served **dynamically** at `/tonconnect-manifest.json`
(`app/tonconnect-manifest.json/route.ts`) and derives `url`/`iconUrl` from the request origin, so it
always matches the deploy domain — there's no static file to edit. The icon is `public/icon.png`
(swap it if the KOL wants their own branding).

After deploy, confirm `https://<app>/tonconnect-manifest.json` is publicly reachable and shows the
correct origin. Leave `NEXT_PUBLIC_TONCONNECT_MANIFEST_URL` unset.

## 7. Post-deploy verification (inside Telegram)

Open the Mini App from the bot (the Telegram-only features need to run **inside Telegram over HTTPS**):

- [ ] `https://<app>/tonconnect-manifest.json` loads and shows the right origin.
- [ ] Open the Mini App → seamless Telegram login produces an EVM address (header chip).
- [ ] Connect a TON wallet → `ton_proof` verifies (TON ✓ chip).
- [ ] "Add funds" → quote shows → sign in TON wallet → USDC appears in the embedded wallet.
- [ ] (If the perps builder fee is enabled) the builder's Hyperliquid account holds ≥ 100 USDC (§4) — otherwise fee-bearing orders reject.
- [ ] Perps tab loads live Hyperliquid markets → place a small order (USDC @ Arbitrum).
- [ ] Spot/RWA tab loads live markets → place a small tokenized order (USDC @ Ethereum); the **MAX** button fills the input.
- [ ] Withdraw → enter amount → funds pulled from product → bridged EVM→TON → arrive in TON wallet.
- [ ] History: tap the activity icon on **Spot** and **Perps** → past trades / transfers list, newest first.
- [ ] (If fees enabled) after a spot **sell**, `NEXT_PUBLIC_TOKENIZED_FEE_ADDRESS` receives USDC; after a perps **close**, the builder address collects its fee.
- [ ] No "sign" prompt from Privy at any point (only the TON Connect signature on deposit).

If a TON wallet connects but shows grey/disconnected in the app, a per-wallet bridge host is likely
blocked — check the `connect-src` CSP allowlist in `next.config.ts` (each wallet uses its own bridge).

If an action shows **"Unauthorized — verify your wallet first,"** the signed-session cookie lapsed
(reads don't need it; signing a trade does). The app now **self-heals from Telegram `initData` on
load**, so reopening/refreshing the Mini App clears it — no config needed beyond `TELEGRAM_BOT_TOKEN`
(§2) and `NONCE_SECRET` (§5b) being set so sessions verify across serverless instances.

If a spot **equity** (Ondo, e.g. TSLAon) order is blocked with a *market closed* banner, that is
**expected outside U.S. market hours** — Buy/Sell re-enable at the next session. **Midas RWA**
(mTBILL/mBASIS/mBTC) is unaffected and trades anytime, so verify spot with a Midas asset off-hours.

## 8. Secret rotation & off-boarding

- **Telegram bot token** — BotFather `/revoke` → update `TELEGRAM_BOT_TOKEN` (and Privy's Telegram
  login config) → redeploy.
- **Privy** — rotate the app secret and authorization key in the Privy dashboard; update
  `PRIVY_APP_SECRET` / `PRIVY_AUTHORIZATION_KEY` → redeploy. Rotating the **authorization key** changes
  the signer for existing delegated wallets — coordinate carefully.
- **Compass API key** — Compass rotates/revokes server-side; KOL updates `COMPASS_API_KEY` → redeploy.
- **`NONCE_SECRET`** — rotating it invalidates in-flight sessions/nonces (users re-auth); otherwise safe.
- **`GAS_SPONSOR_PK`** — keep the sponsor wallet funded; rotate if leaked.

Never commit real secrets. `.env.example` is the canonical list; `.env.local` is gitignored.
